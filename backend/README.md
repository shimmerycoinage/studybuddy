# Серверная часть

Бэкенд StudyBuddy использует FastAPI, PostgreSQL и SQLAlchemy. Миграциями базы данных управляет Alembic. [Каркас бэкенда в Linear](https://linear.app/ekaterina-rogozinnikova/issue/SB-5/karkas-bekenda-m)

## Локальный запуск

Запустите Docker Desktop и откройте PowerShell в корне репозитория, где лежит `docker-compose.yml`. При первом запуске выполните все шаги. Если `.env` с `JWT_SECRET` уже настроен, начните с шага 3.

1. Сгенерируйте секретный ключ для подписи JWT. Для этой команды нужен Python 3.

   ```powershell
   python -c 'import secrets; print(secrets.token_hex(32))'
   ```

2. Создайте файл `.env` рядом с `docker-compose.yml`. Вставьте сгенерированную строку после `JWT_SECRET=` без пробелов.

   ```dotenv
   JWT_SECRET=ваш_сгенерированный_ключ
   ```

3. Соберите и запустите бэкенд и PostgreSQL.

   ```powershell
   docker compose up --build -d backend
   ```

   При запуске бэкенд автоматически применит миграции базы данных.

4. Откройте [проверку состояния](http://localhost:8000/health). Если сервер подключился к PostgreSQL, вы увидите `{"status":"ok"}`.

## SB-6 — API регистрации и входа

Пользователь регистрируется по имени, email и паролю. Бэкенд сохраняет хеш пароля с помощью bcrypt и при успешном входе выдаёт JWT для доступа к защищённым маршрутам.

| Маршрут | Результат |
| --- | --- |
| `POST /register` | Принимает `name`, `email` и `password`. Возвращает `201` и поля `id`, `name`, `email`. Если email уже зарегистрирован, возвращает `409`. |
| `POST /login` | Принимает `email` и `password`. Возвращает `200`, `access_token` и `token_type`. При неверном email или пароле сервер возвращает `401`. |
| `GET /me` | По токену возвращает `200` и профиль текущего пользователя. Без действительного токена возвращает `401`. |

### Быстрая проверка в Swagger

Откройте [Swagger](http://localhost:8000/docs) и используйте тестовые данные.

1. Через `POST /register` создайте аккаунт с новым email. Ожидаемый код — `201`.
2. Через `POST /login` войдите с тем же email и паролем. Ожидаемый код — `200`. Скопируйте значение `access_token` из ответа.
3. Нажмите **Authorize** и вставьте токен без кавычек и без слова `Bearer`. Затем выполните `GET /me`. Ожидаемый код — `200`, в ответе будут `id`, `name` и `email` вашего аккаунта.

## SB-11 — API учебных групп

Пользователь может создать группу или вступить в неё по коду приглашения. Создатель получает роль `owner`, остальные участники — `member`. Для всех маршрутов нужен JWT.

| Маршрут | Результат |
| --- | --- |
| `POST /groups` | Создаёт группу и назначает создателя владельцем. В ответе приходит код приглашения `invite_code`. |
| `POST /groups/join` | Принимает `invite_code` и добавляет пользователя с ролью `member`. Неверный код даёт `404`, повторное вступление — `409`. |
| `GET /groups` | Возвращает группы текущего пользователя и число участников каждой группы. |
| `GET /groups/{group_id}` | Для участника возвращает детали группы, `member_count` и его роль `my_role`. Посторонний пользователь получает `404`. |
| `DELETE /groups/{group_id}/membership` | Участник выходит из группы. При выходе владелец передаёт ID другого участника в параметре `new_owner_id`. Передача прав и выход сохраняются одной транзакцией. |
| `DELETE /groups/{group_id}/members/{user_id}` | Владелец исключает участника. При успехе сервер возвращает `204`, при попытке исключения со стороны обычного участника — `403`. |

### Быстрая проверка в Swagger

1. Войдите под первым аккаунтом и передайте токен через **Authorize**. Создайте группу через `POST /groups` и сохраните `id` и `invite_code` из ответа.
2. Войдите под вторым аккаунтом, смените токен в **Authorize** и передайте `invite_code` в `POST /groups/join`.
3. Выполните `GET /groups/{group_id}` с сохранённым `id`. У новой группы с двумя участниками ожидаются `"member_count": 2` и `"my_role": "member"` для второго аккаунта.

## SB-15 — API вопросов и ответов

Участники группы могут задавать вопросы, читать обсуждение и отвечать друг другу. Отметить вопрос решённым может только его автор. Для всех маршрутов нужен JWT.

| Маршрут | Результат |
| --- | --- |
| `POST /groups/{group_id}/questions` | Создаёт вопрос в группе. Принимает `{"body": "Текст вопроса"}`. Возвращает `201` и созданный вопрос с `"is_resolved": false`. |
| `GET /groups/{group_id}/questions` | Возвращает страницу вопросов группы, начиная с самых новых. Поддерживает параметры `status`, `page` и `page_size`. |
| `POST /questions/{question_id}/answers` | Добавляет ответ. Принимает `{"body": "Текст ответа"}`. Возвращает `201` и сохранённый ответ. |
| `GET /questions/{question_id}/answers` | Возвращает ответы от ранних к поздним. У каждого есть `author_id`, `author_name` и `created_at`. Если ответов ещё нет, вернётся `200` и `[]`. |
| `PATCH /questions/{question_id}/resolve` | Автор отмечает свой вопрос решённым. Тело запроса не требуется. Возвращает `200` и вопрос с `"is_resolved": true`. |

### Фильтры и страницы

- `status=all` — все вопросы группы. Это значение по умолчанию.
- `status=unanswered` — вопросы, у которых ещё нет ни одного ответа.
- `status=resolved` — вопросы, которые автор отметил решёнными.
- `page` — номер страницы, начиная с `1`. `page_size` — от `1` до `100`, по умолчанию `10`.

Например, `GET /groups/7/questions?status=unanswered&page=2&page_size=5`
вернёт вторую страницу вопросов без ответа в группе `7`, до пяти вопросов.
Номер группы для своего запроса можно взять из `GET /groups`.

### Быстрая проверка в Swagger

1. Войдите под участником группы, передайте токен через **Authorize** и создайте вопрос. Сохраните `id` из ответа.
2. Войдите под вторым участником той же группы, смените токен в **Authorize** и ответьте на вопрос. Откройте
   список ответов и проверьте имя автора и время. После первого ответа вопрос
   должен исчезнуть из `status=unanswered`.
3. Под вторым участником вызовите `PATCH /questions/{question_id}/resolve` —
   ожидается `403`. Повторите запрос под автором — ожидается `200`.
4. Откройте список с `status=resolved` и найдите вопрос по сохранённому `id`.

Без действительного токена сервер вернёт `401`. Для пользователя вне группы
её вопросы недоступны (`404`). Пустой текст или строка из пробелов при создании
вопроса или ответа дают `422`.

## SB-18 — API материалов группы

Участники группы могут загружать файлы, просматривать их список и скачивать материалы. Удалить материал может только его автор. Поддерживаются PDF, DOCX, PPTX, PNG и JPG размером до 10 МиБ включительно. Файлы хранятся в томе Docker `materials_data`, сведения о них — в PostgreSQL. Для всех маршрутов нужен JWT.

| Маршрут | Результат |
| --- | --- |
| `POST /groups/{group_id}/materials` | Принимает файл в поле `file` формы `multipart/form-data`. Возвращает `201`, номер материала `id`, исходное имя `original_name` и размер `size_bytes`. |
| `GET /groups/{group_id}/materials` | Возвращает `200` и материалы выбранной группы. У каждого файла есть `id`, `group_id`, `original_name`, `size_bytes`, `author_id`, `author_name` и `created_at`. Сначала идут новые материалы. При одинаковом времени первым идёт материал с большим `id`. |
| `GET /materials/{material_id}/download` | Участник группы скачивает исходный файл с его оригинальным именем. При успехе сервер возвращает `200`. |
| `DELETE /materials/{material_id}` | Автор удаляет файл из хранилища и запись из базы. При успехе сервер возвращает `204` с пустым телом. Другой участник группы получает `403`. |

### Быстрая проверка в Swagger

1. Войдите под владельцем группы и передайте токен через **Authorize**. Выполните `GET /groups/{group_id}/materials` для группы без материалов. Ожидайте `200` и пустой список `[]`.
2. В группе с материалами выполните тот же GET. Найдите файл по `id` из ответа при загрузке. Сверьте имя, размер и автора. Если файлов несколько, проверьте, что самые новые идут первыми.
3. Смените токен на токен другого участника той же группы и повторите GET. Ожидайте `200` и тот же список. У каждого файла должно остаться имя человека, который его загрузил.
4. Под пользователем вне группы запросите её список. Ожидайте `404`. Для несуществующей группы сервер также вернёт `404`. После **Authorize → Logout** повторите запрос — ожидайте `401`.
5. Войдите под первым участником, установите его токен в **Authorize** и загрузите тестовый файл. Сохраните `id` материала. Смените токен на токен второго участника той же группы и скачайте файл. Ожидайте `200`. Сверьте исходное имя файла и сравните SHA-256 исходного файла и скачанной копии. Значения должны совпасть.
6. Под вторым участником попробуйте удалить этот материал. Ожидайте `403`. Сразу повторите скачивание. Файл по-прежнему доступен (`200`).
7. Смените токен на токен автора и удалите материал. Ожидайте `204` с пустым телом. Повторите скачивание по тому же `id`. Ожидайте `404`.

## SB-20 — Сервер совместного редактирования конспектов

Участники группы могут создавать конспекты, видеть их список и одновременно редактировать один текст. FastAPI проверяет JWT и членство в группе конспекта. Сервер объединяет двоичные правки Yjs с помощью `pycrdt` и сохраняет состояние в PostgreSQL в поле `notes.yjs_state`.

| Маршрут | Результат |
| --- | --- |
| `POST /groups/{group_id}/notes` | Принимает `{"title": "Производные"}`. Возвращает `201` и поля `id`, `group_id`, `author_id`, `title`, `created_at`. Автор определяется по JWT. Пустое название или строка из пробелов даёт `422`. |
| `GET /groups/{group_id}/notes` | Возвращает `200` и список конспектов группы, начиная с самых новых. Если конспектов ещё нет, вернётся `[]`. |
| `WS /ws/notes/{note_id}` | Подключает участника к выбранному конспекту. Клиент передаёт `studybuddy-notes-v1` и JWT в заголовке `Sec-WebSocket-Protocol`. Сервер проверяет права при подключении и перед обменом правками. |

После подключения сервер отправляет `ready`. По запросу `sync` вкладка получает сохранённое состояние, если оно есть, а затем сообщение `synced`. После записи правки в PostgreSQL сервер рассылает её остальным участникам этого конспекта и отправляет автору правки подтверждение `saved`.

### Быстрая проверка в Swagger

1. Подготовьте двух участников одной группы. Войдите через `POST /login` под первым участником и установите токен в **Authorize**. Возьмите `group_id` из `GET /groups`.
2. Создайте конспект через `POST /groups/{group_id}/notes`. Ожидайте `201` и сохраните `id` конспекта для проверки в браузере.
3. Под вторым участником выполните `GET /groups/{group_id}/notes`. Ожидайте `200` и тот же конспект с исходным `author_id`. Для пользователя вне группы оба HTTP-маршрута возвращают `404`, без действительного токена — `401`.

### Проверка совместного редактирования и сохранения

1. Запустите бэкенд по инструкции «Локальный запуск». Для тестовой страницы нужен фронтенд на `http://localhost:5173`. Если он ещё не запущен, откройте отдельный PowerShell в корне репозитория и выполните:

   ```powershell
   cd frontend
   npm.cmd install
   npm.cmd run dev -- --port 5173 --strictPort
   ```

2. В двух браузерах или отдельных профилях войдите через [страницу входа StudyBuddy](http://localhost:5173/src/pages/login.html) под разными участниками группы. В обоих откройте [тестовый конспект](http://localhost:5173/notes-demo.html?note=1), заменив `1` после `?note=` на сохранённый `id` конспекта. Дождитесь надписи «Конспект загружен из базы». Проверьте, что номер конспекта совпадает, а номера пользователей различаются.
3. В первом браузере добавьте строку. Во втором она должна появиться в течение секунды без обновления страницы. Добавьте другую строку во втором браузере и проверьте её в первом. При попытке открыть тот же конспект под пользователем вне группы WebSocket отклоняет подключение.
4. Дождитесь надписи «Сохранено в PostgreSQL» у каждого автора правки и закройте обе вкладки с конспектом. Из корня репозитория выполните `docker compose restart backend`. Когда [проверка состояния](http://localhost:8000/health) вернёт `{"status":"ok"}`, откройте тот же конспект в одной вкладке. Обе строки должны восстановиться из базы.
